# 打开 PDF 与 Beamer 翻页的原生 A/B 结果

Windows 11 上，用同一份 100 页 Beamer 文稿测量 FerroStage 的真实讲者与观众窗口。新进程打开到首张讲者预览的中位数从 **243.0 ms 降到 148.1 ms**；连续翻页输入到观众开始绘制转场，从 **48.0 ms 降到 7.7 ms**。计时取自应用的单调时钟。

| 路径 | 每版本次数 | 之前，中位 / P95 (ms) | 之后，中位 / P95 (ms) |
|---|---:|---:|---:|
| 新进程接受打开 → 首张讲者预览 | 20 | 243.0 / 284.6 | 148.1 / 158.5 |
| 返回首页，从最近文稿重开 → 首张讲者预览 | 20 | 240.6 / 262.0 | 139.4 / 150.0 |
| 开始放映 → 观众首张 | 20 | 134.1 / 142.5 | 101.3 / 115.5 |
| 连续向前翻步 → 观众 FirstVisible | 200 | 48.0 / 66.3 | 7.7 / 14.0 |
| 重复往返翻步 → 观众 FirstVisible | 200 | 41.0 / 65.6 | 4.2 / 9.0 |
| 连续向前翻步 → 目标页转场完成 Settled | 200 | 355.4 / 655.1 | 310.7 / 615.6 |
| 重复往返翻步 → 目标页转场完成 Settled | 200 | 343.5 / 367.4 | 306.8 / 311.7 |

### 等待发生在哪里

从讲者提交一次翻页到新的公开帧进入绘制，之前有两次等待 25 ms 维护定时器的机会。现在 shell 在导航成功并改变目标页时立即调度；worker 写入原结果通道后发送容量为 1 的唤醒信号。前台沿用原有请求身份、代数和裁切校验取回结果。定期维护继续处理显示器、计时与热重载。缓存预算、PDFium 单线程、画面分辨率和作者转场都与基线一致。

| 连续翻步分段 | 之前中位 (ms) | 之后中位 (ms) |
|---|---:|---:|
| 选定目标 → 提交观众请求 | 13.56 | 0.02 |
| 提交 → 前台取回结果（含排队与实际光栅） | 30.99 | 2.64 |
| 前台取回 → 首个转场绘制 | 3.19 | 4.51 |

末段中位数增加了 1.32 ms，两段调度等待的减少带来了整体收益。按实际 worker 命中日志分组，命中的 220 次翻步从 41.56 ms 降至 4.19 ms，未命中的 180 次从 45.30 ms 降至 7.94 ms。连按每组三次，共 20 组；两个版本均有 40 个被后续输入取代的中间目标，全部 20 个最终目标均成功绘制。常规采样均完成，无超时。

打开文稿时，元数据回复到首张候选光栅回复的中位间隔从 31.26 ms 缩短为 4.93 ms；到候选提交回复的下一段从 45.91 ms 缩短为 9.43 ms。优化后的候选准备到收到元数据仍需 **112.51 ms**，其中含 PDFium 全文稿的元数据读取与回复交付。之前的[底层实测](findings.md)已定位到逐页几何、旋转和标签读取。此轮保留该校验，避免影响旋转页、备注裁切与 overlay 分组。

### 测量条件与可复核性

- 输入为 `fixtures/pdf/perf-100.pdf`，SHA256 为 `395d8bb26ad5f8f7ca5245901abdcb8de1fccd2be5ff7e30482e54f776526cb6`。使用锁定的 Windows x64 PDFium 与相同 Rust release 特性 `gpui,pdfium`。基线为提交 `e6cf226626f2df279d0102a41233659446bb1caf` 加相同的本地计时点。两个 EXE、DLL 和输入的哈希记录在结果 JSON。
- 按 **A1 → B1 → B2 → A2** 顺序测量，每批 10 个进程。每个进程用独立设置，通过正常入口打开并重开一次，发送 F5、PageDown、PageUp；每批记录 100 次向前和 100 次往返，以最近秩计算 P95。新进程样本没有清操作系统文件缓存。顺序翻页会经过不同复杂度和转场的页面，本次每进程向前遍历 10 步。
- 新进程首张实际预览为 756×213 像素，进程内重开为 740×208；观众请求目标为 1200×1140。按操作分别核对 A、B 两组尺寸，本文使用同样的 L1/L2/缩略图预算（256/512/64 MiB）。两次基线的连续翻页中位数为 45.88、50.64 ms，两次候选为 7.64、7.79 ms。新进程打开的两次基线为 239.18、246.52 ms，两次候选为 141.42、149.24 ms。
- `FirstVisible` 是目标导航首次成功绘制的转场帧，起点可能仍显示上一页；`Settled` 才是完整目标页绘制。两者都在应用内计时。没有测键盘硬件延迟、操作系统 Present、物理投影仪或其他平台。
- [汇总和各批统计](native-ab.json) · [40 个进程的原始日志及样本](native-ab-raw.zip) · [采样驱动](native_benchmark.py) · [统计脚本](compare_runs.py) · [打点协议](trace-events.md)。

从仓库根使用 `native_benchmark.py --exe <release-exe> --out <fresh-directory> --processes 10 --reopens 1 --forward 100 --repeat 100 --warmups 2 --burst 3` 重复各批。驱动只操作测试进程的窗口。把原始 ZIP 解压到独立目录，即可用 `compare_runs.py --before <dir>/perf-a1 <dir>/perf-a2 --after <dir>/perf-b1 <dir>/perf-b2 --output comparison.json` 重新计算。
