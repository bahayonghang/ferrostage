二、产品范围和技术边界
- PDF/Beamer 展示；没有 LaTeX 编辑、编译器调用、PDF 注释编辑或写回。
- 用户 PDF 只读；会话画笔只在内存。设置文件可以原子保存。测试夹具的写入须限制在独立临时目录。
- Idle → Ready → Presenting；打开 PDF 后不创建观众窗口、不启动计时；显式开始才演示。非演示态观众快照为 Curtain。
- 每屏 MonitorId + MonitorRole；单 Audience；单屏默认 presenter_only；窗口化观众模式必须显式开启。保存的 Audience 缺席时不自动接管其他屏。
- core 保持纯类型、状态机和纯函数，不引入 GPUI、PDFium、lopdf、notify 或 OS API。观众窗口的数据边界不含讲者备注。
- 以仓库 pin 为准：Rust 1.99.0 / edition 2024、pdfium-render 0.9.4、lopdf 0.45.0、GPUI Zed v1.23.3 或计划允许的 gpui-kit 0.7.3、notify 8.2.0、toml 1.1.8。不顺手升级依赖，不将尚未链接的库描述为已可用。
- 单一 PDFium 渲染线程，BGRA8；媒体共享离屏 BGRA 帧，不创建子 HWND；cargo deny 许可证门禁保留。
- 热重载保持 P2，描述为磁盘 PDF 被外部替换，不绑定任何 LaTeX 工具链。

## Prompt B：检查实施状态，顺序执行全部任务并支持中断恢复

1. 使用 trellis-start；读取 AGENTS.md、RTK.md、当前工作流与相关 spec index。核对 Git 分支、HEAD、git status、未提交 diff、task.py current、task.py list，以及已有会话记录。current 没有任务只是一个状态，不表示整个计划尚未开始。

3. 对照实际代码、研究报告、测试记录与未提交修改，判断每个任务到了哪一步。planning 不证明没有代码；in_progress 不证明仍缺功能；验收勾选或旧模型结语不证明当前代码已通过检查。证据缺失、失败或被后续修改影响时，先做针对性检查再决定恢复点。

5. 修复功能错误先建立可复现回归测试，按步骤运行相关 crate 检查。仅文档变更检查链接、表格、契约和语义，不新增形式化测试。按项目质量门禁运行 just ci，以及本任务声明的编译、动态库和实机验证。没有新改动或未解决问题时，不无意义重复已通过检查。

7. 更新该子任务验收与 execution-state.md，标明实现、自动检查、人工检查和提交/归档分别处于何种状态。随后自动选择下一个可执行任务，不以“是否继续下一个任务”的问题结束。

五、阶段门禁与父任务集成
1. 02/03/04 的相关交付物就绪后运行 Gate A：核心、设置和拓扑契约及测试。

## 推荐使用顺序

先运行 Prompt A。任务设计核对通过后，使用 Prompt B 连续实施全部子任务；中断后再次使用 Prompt B 自动核对进度并续做：

`01 → 02 → 04 → 03 → 05 → 06 → 07 → 08 → 09 → 10 → 11`

这是顺序实施时的可行顺序，仍以修订后的依赖与 Gate 为准。单个子任务内部按平台的 Trellis 执行模式实施和检查，子任务之间顺序推进。每个步骤把进度写入父任务 execution-state.md；实现与集成验证完成后，提交和归档另行收尾。
